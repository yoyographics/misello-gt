## 5. PRICING AND INVOICING

- **All prices are final** — include VAT (12%), shipping, and production. No surprises at checkout.
- **No "Consumer Final / CF" option** — the customer must enter a NIT or CUI.
- **Electronic invoice (FEL)** issued by Tekra S.A.
- Price **does not vary by design complexity**.
- Base prices come from the `medidaspreciossellosfinal.ods` file.
- **Quantity discounts:** Configurable from the control panel (percentage or fixed amount).
- **Promotional discounts:** Time-limited or per model, configurable from the control panel.

## 6. TECHNICAL DESIGN AND PRODUCTION CONSTRAINTS

### 6.1 Minimum character size
- **2mm = 41 pixels at 600 dpi** — minimum engravable
- The system **validates automatically** before allowing the customer to proceed

### 6.2 Minimum line thickness
- **1 typographic point = 9 pixels at 600 dpi**

### 6.3 Colors and logos
- Production file: **SVG black and white at 600 dpi**
- Logos with gradients/shadows/transparency → automatic conversion to B&W
- The system warns the customer before converting
- Low-resolution logos → redrawn by design team (1 additional business day)

### 6.4 Fonts
- Only **authorized and tested** fonts for laser engraving
- Uploaded from the control panel by the administrator

### 6.5 Curved text
- Curved/arc text is supported — the renderer generates it automatically

### 6.6 Languages and special characters
- Spanish: ñ, á, é, í, ó, ú, ü, ¿, ¡
- Mayan languages: Q'eqchi', Kaqchikel, Mam

### 6.7 Production file vs. preview file

| Type | Format | Use |
|------|--------|-----|
| Preview | Color PNG/SVG | Shown to customer and sent by email |
| Production file | B&W SVG, 600 dpi, exact model size | Sent to laser engraving machine |

### 6.8 Manufacturing technology
- High-precision laser technology — **NOT mentioned to the customer**

## 7. CUSTOMER PURCHASE FLOW

### 7.1 Pre-authentication (no login required)
The customer can: browse catalog, see prices, select ink color, explore models.

### 7.2 Authentication point
Before selecting a template or using the design assistant → **Google OAuth is required**.
Shipping data is collected at the end during checkout.
If the browser is closed mid-order: progress is saved as a "pending order" in their account.

### 7.3 Design flow — maximum 4 steps

```
STEP 1: What is your stamp for?
        (Category: professional, company, address, signature, institutional, etc.)
              ↓
STEP 2: Choose your model
        (Only models compatible with the chosen category)
        Price is visible from this point
              ↓
STEP 3: Customize your design
        - Enter text line by line
        - Upload logo if applicable
        - Choose ink color (based on inventory)
        - Real-time preview
        - Silent technical validation
              ↓
STEP 4: Final view + confirmation
        "Add to cart" button
```

### 7.4 Special cases

**Professional stamp (colegiado):** Customer enters their professional association requirements or uploads a photo. The system suggests the most suitable model.

**Government institutions:** Checkout collects data but does NOT charge the card. Requires manual admin approval.

**Lawyer stamp replica:** Only the person themselves can place the order. A high-resolution photo of the previous stamp is required. The additional price is editable from the panel.

**Out-of-stock products:** Shows "Out of stock" + email field + "Notify me" button. Generates internal team notification and a waitlist entry in the panel.

## 16. TECHNICAL ARCHITECTURE

```
CLIENT (web — Next.js)
     ↓
GOOGLE AUTHENTICATION (OAuth 2.0 — public customers only)
     ↓
DESIGN ASSISTANT (Claude API — claude-sonnet-4-6)
Claude receives: category, text, logo, chosen model
Claude generates: structured JSON with all design parameters
     ↓
DETERMINISTIC RENDERER (NestJS server)
Receives JSON → generates:
  - Production SVG (B&W, 600dpi, exact model size in px)
  - Preview PNG (color, to show to customer)
     ↓
TECHNICAL VALIDATOR (automatic before production)
✓ Minimum character size (≥2mm / ≥41px at 600dpi)
✓ Minimum line thickness (≥1pt / ≥9px)
✓ Dimensions within model range
✓ Text confirmed by customer
✓ Logo converted to B&W if it has gradients
     ↓
CHECKOUT → PAYMENT (Pagalo.gt) → FEL INVOICE (Tekra) → CONTROL PANEL → PRODUCTION
```

> Claude does NOT generate the SVG directly. It generates a JSON with parameters → a deterministic renderer produces the final SVG. This guarantees +99% production accuracy.

## 18. BACKEND MODULES (NestJS)

The backend is divided into 8 modules. Each module has its own folder in the project.

### Module 1 — Auth (`/auth`)
Authentication of public customers (Google OAuth) and internal panel users (JWT).

### Module 2 — Catalog (`/catalog`)
Products, models, prices, stock. Data source: database (loaded from the ODS file).

### Module 3 — Design Assistant (`/design`)
- Claude API call → receives JSON parameters
- Deterministic renderer → generates production SVG and preview PNG
- Automatic technical validator

### Module 4 — Orders (`/orders`)
Full lifecycle: draft → pending payment → payment received → confirmed → in production → finished → shipped.

### Module 5 — Payments and Invoicing (`/payments`)
- Pagalo.gt integration (card)
- Tekra S.A. integration (FEL — electronic invoice)
- NIT/CUI validation with Tekra before invoicing

### Module 6 — Inventory (`/inventory`)
Stock of mounts, ink pads, inks. Automatic decrement per confirmed order. Low stock alerts.

### Module 7 — Notifications (`/notifications`)
Transactional emails in 3 stages. Editable templates. Manual send from panel (stages 2 and 3).

### Module 8 — Control Panel (`/admin`)
Private API for the internal team. Order management, payments, inventory, users, discounts, fonts, T&C, waitlist.

## 21. DEVELOPMENT RULES FOR CLAUDE CODE

These rules apply to ALL code generation in this project:

1. **Code language:** Comments in Spanish. Variable names, functions, and classes in English (industry standard).
2. **Never hardcode credentials** — always use `process.env.VARIABLE_NAME`.
3. **Prisma is the only database access layer** — never write raw SQL.
4. **All panel endpoints (`/admin/*`) must verify the JWT and the user's role** before executing any logic.
5. **All DTOs (incoming data objects) must have validation with `class-validator`**.
6. **Files uploaded by the customer are validated by both extension AND actual MIME type** (not just the filename).
7. **The payments module never stores CVV or full card number** in any table.
8. **Rate limiter is applied to all public endpoints**, especially the panel login.
9. **Each module has its own tests** (at least unit tests for business logic).
10. **The SVG renderer is deterministic** — the same input JSON always produces the same SVG output.
